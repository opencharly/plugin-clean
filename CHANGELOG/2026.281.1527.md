## Summary

`plugin-clean` owns `charly clean` and the shared retention engine. This is the C6 cutover: two
defects, one mechanism, one PR — plus the candy's own declaration surface (description, ADE `check:`,
README), which moved with the code because a plugin's declarations are published docs. This head
also carries the fix round for the review BLOCK on `0dfd050a` (blocks 2, 3 and 4; block 1 is the bed
result below, and its one failure is named with the owner that can fix it).

**1. Image-tag retention no longer orders by `ai.opencharly.version` (#10).** The label is a
cutover-boundary artifact: the schema-versioning-removal cutover deleted the author-declared
aggregated image version it carried, so nothing emits it, while images built before that cutover
still carry it. Ordering by it therefore made the **labelled (older)** row outrank an **unlabelled
(newer)** one regardless of build time — an inversion under which `keep_images` selects the NEWEST
image for removal and keeps the oldest. Identity is now **one content-identity helper** — the
image-config digest the engine reports as the image ID, which is the identity `retentionRanks`
already used (no second key invented) — recency is **creation time** (the only key total over the
tags charly mints: `--tag` REPLACES the CalVer tag, so a bed build's `check-<bed>-<calver>` parses as
no CalVer at all), and the undatable-tag exemption guards on the build tag alone instead of an AND
with a key nothing emits.

**2. A new `scopes` category reaps a hung transient build scope (#11).** A `charly box build` runs
through buildah/podman, which puts each BUILD CONTAINER into its own transient systemd user scope
named `<runtime>-buildah-<id>.scope`. A build step that hangs leaves that scope running FOREVER —
the only thing that would have stopped it died with the builder, and the run metadata that
`charly reap-orphans` scans is gone with the worktree. Measured in the issue: one scope ACTIVE for
seven days, a spinning `npm install` at 309% CPU, 12.27 load on 16 cores. The category stops a scope
only when it is in that family AND has been ACTIVE for at least **1h** AND **no `buildah`/`podman`
builder process is alive anywhere on the host**; it also declines wholesale while charly's own
build-activity lock is held. It runs on a plain `charly clean` and with `--deep`, and any other
explicit category suppresses it.

**3. The engine is resolved only for the categories that touch the container store.** Review block 3
was right and it was a real defect, not a wording slip: `runRetentionOutcome` resolved the engine
unconditionally, so `charly clean --scopes` — and `--check` and `--cache` — died with an
engine-resolution error on a host whose podman is absent or broken. That is exactly the host most
likely to carry a hung build scope, since a hung scope is the residue of a build that already
failed. Resolution now happens only for `--images`/`--deep`/`--invalidate`/`list`, which makes the
two documented claims true by construction rather than by assertion, and
`TestScopesOnlyRunNeedsNoEngine` pins it with an images-only negative control.

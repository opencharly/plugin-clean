# 2026.322.1315 — feat(clean): implement D-STORE-7 (--store) and route cache sweeps by store identity

## Summary

`charly clean` now implements **`D-STORE-7`** (`DESIGN.md:2488`) — *"keeps what state references and
evicts the rest within a size budget; locks die with their holder"* — for the charly image store,
and the `--cache` sweep no longer destroys that store's content (`opencharly/plugin-clean#27`).
The two are one story seen from both ends: **`charly clean` reclaims what is unreferenced and never
destroys what is live.** A sweep that deletes a live image's bytes and a budget that evicts a
referenced entry are the same defect class.

The row was implemented **nowhere**: `keep_images`/`keep_check_runs` count TAG ROWS in the
*engine's* storage, and no size budget existed in any schema or code. The image store — the
`registry` named store under the cache root, one immutable entry per build that a rebuild APPENDS
to rather than replaces — therefore grew by one artifact per rebuild forever. `#21`'s re-scope
records the operator's measurement on this host (619 GiB, 1609 entries, 66 image families, nothing
ever removing one); the pre-rename store beside it, which I read while designing this, carried the
same 66 families across 172 entries.

### 1. `--store` — the entry policy

| Keep-set surface | What it is | Why it is in the inventory |
|---|---|---|
| the container engine (`podman ps -a`) | every container, running or stopped: its image ref and its image ID | the runtime truth a deploy actually runs — what `charly status --json` publishes as `image_ref` |
| the quadlet units (`deploykit.QuadletDir()`, `charly-*.container`, `Image=`) | the unit charly wrote for each pod deploy | the only record of an ENABLED deploy whose container does not exist yet (a `status --all` row carries no `image_ref`) |

Every state reference is resolved to an entry through **`ImageStore.Lookup`** — the store's own "the
newest entry whose annotation names this reference" — because state names a REFERENCE while the
store keys on the artifact's DIGEST. That resolution is also what makes a *superseded rebuild of a
referenced tag* reclaimable (five entries under `vision-gate`: the name resolves to the newest, the
older four are evicted with the reason `superseded: …`). An entry whose own content address a
container names is kept outright. An entry with no `io.containerd.image.name` annotation is kept as
`unclassifiable` — the only verdict that cannot be wrong.

A state reference that names a bare REPOSITORY — a quadlet's `Image=vision-gate`, or a digest-only
reference `normImageRef` folds to one — keeps **every tag of that repository**, and that match is
checked BEFORE the exact-tag one: the state named the repository, not one build of it, and a build a
bare reference covers may not be evicted on a guess. The price is that a bare reference also protects
superseded rebuilds; that is the conservative direction, and it is the one that cannot delete a
deployment.

**The refusal is the contract, not a fallback.** An unreadable surface is not an empty one: "nothing
is referenced" is how a sweep deletes the image a running deployment was built from. A failed
`podman ps`, a quadlet that cannot be read, a charly quadlet with no `Image=` line, an index that
disagrees with its own entries, or a store that cannot be enumerated **aborts the whole sweep** with
an error naming the surface and the path, and evicts nothing. `--dry-run` refuses on exactly the same
inputs. A live build makes the sweep **decline** (`SKIPPED`, in place of its count), because an
artifact's blobs are published before its entry.

**The budget is authored, and it never authorises evicting live state.** `schema/clean.cue`
`#CleanPlugin.store_budget.bytes` (32 GiB) — CUE first, the Go derived from it, no constant. The
sweep reports the RETAINED bytes against it and says `within budget` or `OVER budget by <bytes>`;
being over budget is reported, never "fixed", because the entries left are the ones state
references. `--store` declares `bare: false`, so it never fires on a plain `charly clean`.

**What a dry run can and cannot say.** The DECISION is identical in both modes (same entries, same
reasons — pinned by mutation). The BYTE figure is not: a dry run measures the store as it is
(`N held of <budget>`) plus the blobs already unreferenced, while the retained size after eviction
needs the eviction — the store's public surface cannot size a hypothetical entry set without
deleting it, and a number that looked like the post-sweep size while being the pre-sweep one is the
kind of figure this report exists to avoid. The real run measures both exactly.

### 2. `--cache` — one reader per store, chosen by IDENTITY (`#27`)

`gcCacheStores` used to sweep in two halves and to **skip** the storekit half whenever the two store
roots resolved to the same directory. With `D-STORE-1`'s one resolver (`DESIGN.md:2482`) that is
*always*: `cache.StoreRoot()` and `storekit.CacheDir()` both return `storeroot.CacheDir()`. So every
host handed the storekit-written `registry` store to `spec/cache`'s image-blind `GCStats`, which
deleted a live image's manifest, config and layers and left the entry answering `Lookup(ref)` for
bytes that were gone. The mirror mistake was equally reachable: `storekit.NamedStores()` lists the
`spec/cache` layouts too, and storekit's reader would have decoded their manifests as empty entries
and freed their payloads.

The reader is now chosen from **the store's own index** (`classifyStore`): every descriptor an
`application/vnd.opencharly.store.entry.v1+json` entry manifest → storekit; every descriptor an OCI
image manifest → `spec/cache`; anything else (a mixed index, an unknown media type, an unreadable
index) → **refused and reported by name**, never swept. The two enumerations are deduped into ONE
inventory by resolved directory, so no store is skipped and none is swept twice, and `sameStoreRoot`
is deleted. Because the image store is never opened by `spec/cache` any more, no `.lock` is written
inside its tree either (`DESIGN.md:2484`). The one per-store reclaim (`sweepStoreBlobs`) is now
shared by `--cache` and `--store` rather than duplicated.

The `--cache` report now NAMES the reader that swept each store (`cache registry (storekit): 3 live
entry(ies); removed 0 unreferenced blob(s) (0 B)`). That is a report-format change on purpose: after
`#27`, "swept by the wrong reader" and "swept by the right one" produced identical lines, so the
fact that matters most was invisible in the product. A consumer that parses `cache <name>:` must be
told.

The same report no longer says `cache: no named cache stores found` when a store WAS found and
refused — those two lines read as "there are none, and here is the one there is". `--store`'s own
report is unaffected.

### Why `go.mod` is not a two-line diff

Two deltas, both mechanical and both named here because an unexplained 30-line `go.mod` change in a
clean-events PR is a fair question:

1. **`go 1.26.4` → `go 1.26.8`.** Not a choice: `github.com/opencharly/sdk@v0.2026322.1227`'s own
   `go.mod` declares `go 1.26.8`, and Go refuses a dependency whose language version is newer than
   the main module's.
2. **The indirect expansion** (`containerd/v2`, `cuelabs.dev/go/oci/ociregistry`, `logrus`,
   `x/oauth2`, `x/sync`, `go-internal`, `errdefs`, `log`). It comes from ONE import this change
   adds: `deploykit` — for `deploykit.QuadletDir()`, the only exported resolver for the quadlet
   directory, which is one of the two state surfaces. `deploykit/vm_box_emit.go` imports
   `sdk/buildkitdrive`, so the whole package's graph comes with it. In the COMPILED-IN placement
   (characters: `command:clean`) the marginal cost is zero — charly already links `deploykit` — and
   it lands only on `cmd/serve`, the out-of-process plugin binary. Resolving the path by hand would
   be a second copy of a rule whose `os.UserHomeDir()` (not `os.UserConfigDir()`) detail a
   hand-rolled version gets wrong, so the narrow fix is filed against the sdk instead:
   **opencharly/sdk#559** (move the pure path helpers to a light package).

### The three assertions `#27` and `D-STORE-3` now carry by name

1. **The store-tree shape, after a REAL sweep.** `TestCleanCacheSweepsTheImageStoreWithItsOwnReader`
   asserts the router (`discoverStores` → `storeReaderStorekit`), the report's reader, the zero
   removed-blob count, every blob the entry reaches still present, and then the directory's
   immediate entries are exactly `{"blobs", "index.json", "oci-layout"}` — `D-STORE-3`
   (`DESIGN.md:2484`) made falsifiable. Its red arm prints the tree, so the `.lock` half is shown,
   not argued: `its tree is now [.lock blobs index.json oci-layout]`.
2. **The refusal arm.** `TestCleanCacheRefusesAStoreItCannotClassify` writes REAL bytes into a store
   whose index mixes descriptor media types, asserts the refusal names it *and* the media types,
   that those bytes are still there afterwards, and that the report carries
   `cache mixed: REFUSED at <dir> — …`. A refusal that only existed as a Go value would be a
   refusal an operator never sees.
3. **The positive/negative pair for `#27`'s data.**
   `TestCleanCacheLookupResolvesToExistingContent` asserts the reference still resolves AND that the
   resolved digest's payload still reads back — the defect's tell was `Lookup(ref) = (digest, true)`
   over deleted bytes. Two tests rather than one because the blob count can be right while the
   reference is dead, and the reference can be live while the graph is missing bytes.

A fourth assertion joined them in round 1, and it is the one the reviewer found missing:
**a bare-repository state reference keeps the repository's TAGGED entries**
(`TestStoreSweepKeepsEveryTagOfABareRepositoryReference`, red arm `mut6`). The previous covering
test used an untagged annotation on both sides, so it could not see the hole: with a bare reference
the bare rule keeps every tag and the superseded path is never reached. It is now a tagged-vs-tagged
fixture (the `Lookup` path) and the tagged-vs-bare pair is the new test's job.

The red arm for all four is the `mut1`/`mut6` block above; the green arm is the same tests on this
head, in the gate fence.

# 2026.322.1645 — feat(clean): ingest the pre-relocation image store instead of abandoning it (#30)

## Summary

**Successor to opencharly/plugin-clean#31**, which the validator auto-closed at its 5-verdict threshold
after each of its findings had been fixed and re-run. Same branch, same head; the only change is this
body naming its predecessor (Part II #7's carry-forward).

`charly clean --cache` now disposes of the **pre-relocation image store** at the data root, which the
store relocation abandoned (`opencharly/plugin-clean#30`: 311 GiB and 202 entries on this host, at a
path no charly verb could name, report or reclaim). The disposition is an **ingest**, not a removal:
every entry is re-published into the cache root's `registry` store, verified there, and only then is
the source tree removed.

### The home, and why it is not `migrate`

The obvious reading — a one-time legacy reshape belongs in `charly migrate`'s declarative table — does
not survive the engine: **every `apply:` hook in `candy/plugin-migrate` is `func(*yaml.Node) bool`**
(`engine.go`'s `goHooks`), i.e. a YAML-document transform applied per file. The engine has no seam for
a filesystem/store operation, so landing this there would mean inventing a second execution class in
`migrate` — a bigger cutover than the issue, and one that would put content-addressed store surgery in
a plugin whose engine knows only YAML. So the work stays in `plugin-clean`, where the store readers,
the reference discipline and the report already live, and the retirement record — the mechanism whose
whole purpose is *"a path a previous version wrote, why it is superseded, and where its content went"* —
gains one row.

### The resolver question, answered explicitly

**There is no data-root resolver, and this change does not add one.** `D-STORE-1` (`DESIGN.md:2482`)
declares four roots — config, cache, state, runtime — and data is **not** among them;
`spec/storeroot`'s `RootData` was reverted for that reason (`opencharly/spec#375`). Asking the contract
to name `$XDG_DATA_HOME/charly` again would re-introduce a root the contract removed.

What remains is a **recorded fact about a dead version**: an old charly wrote its image store under
`$XDG_DATA_HOME/charly/images`. That fact is spelled **once**, as path ELEMENTS in the retirement
record (`retiredCacheRoots()` → `{Name: "data-images", Place: retiredInLegacyDataRoot, Elems:
["charly","images"]}`), and expanded by one function (`legacyDataRoot`) which resolves **no store**,
feeds **no reader**, and is called by the retirement sweep and nothing else. Every cache-root row keeps
resolving through `storekit.StoreDir`; nothing about the live roots changed.

### Why ingest, and not "keep what state references and evict the rest" in place

The issue allows either. The in-place eviction needs a per-entry reachability walk over the **legacy**
layout, whose descriptors are OCI image *manifests* rather than storekit entry manifests — a third
reader, and a second implementation of the image-graph walk that storekit owns privately. It would also
be the only disposition in this package that deletes artifacts on the strength of a keep set, inside a
category (`--cache`) that has no budget, no live-build guard and no refusal discipline of its own.

Ingest needs **no keep set at all**, and that is the point: nothing is dropped. Every descriptor is
re-keyed into the current entry shape (its payload is the artifact index naming the legacy manifest, so
every later reader walks it with the same code), its blobs are materialized into the destination
(hardlinked where the trees share a filesystem, copied otherwise — reported either way), every entry
and every reference is **verified in the destination**, and only then is the source removed. The result
is not a smaller store; it is a store the policy can SEE — `charly clean --store` then applies
`D-STORE-7` (`DESIGN.md:2488`) to it, in the category that owns that judgement.

The refusals are about the bytes it moves, and each names itself: an unreadable `index.json`, an index
that names no entries while the tree holds blobs, an entry with no `io.containerd.image.name`, and an
entry whose manifest the tree does not hold. No state surface is consulted, so none can make the
transform unsafe — the strongest form of the issue's property 3.

## Change classification

**Breaking change + rollback:** not breaking for this repo's consumers. No flag, provider word, wire
type or `verb:retention` shape changes; the served CUE schema is untouched. `--cache` gains one report
line (`cache retired data-images: …`) and one *new* action on a tree no other category touched, so a
consumer parsing `cache retired <name>:` sees a second row where the record now has two. Rollback is
`git revert` of the two commits: the ingest is copy-verify-then-remove, so a reverted binary leaves the
ingested entries in `registry` (where the current binary reads them) and the legacy path gone — no
state to unwind.

**Sequencing:** this is the **producer** half. `opencharly/charly#1203` (the plugin pin bump) is in
flight and gates the consumer side as briefed; no pin is touched here. A `WAITING` comment on this PR
names the block and what clears it (Part II #11).

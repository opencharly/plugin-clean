# 2026.322.2132 — refactor(clean): give the fallback ceiling a name of its own (#35)

## Summary

Closes `opencharly/plugin-clean#35`. The `design-dpat` control counted one definition NAME with two
homes — `#StoreBudget`, declared by `spec/schema/clean.cue:48` and restated by
`candy/plugin-clean/schema/clean.cue` — and rejected it in both places. The census records 7 tolerated
`dup` rows and the control's own words say it is *"lowered, never raised, by the change that fixes it"*,
so the exemption route was closed and the choice was between one home for the name and a distinct name
for the plugin's local shape.

**The choice: a distinct name, `#CleanStoreBudget` — taken because option (1) was tried and MEASURED to
fail, not because it was assumed to, and the duplication that remains is accepted until
`opencharly/sdk#567` removes the limitation that forces it.**

Option (1) is what the contract invites: `spec/spec/cue.mod` exists so *"a consumer … can import the
schema as a package instead of having its text concatenated"*, and four plugin candies already do
(`plugin-task`, `plugin-tunnel`, `plugin-vision`, `plugin-pipeline`). Added here it works for charly's
tooling and fails for the plugin itself:

```
$ charly candy params plugin-clean
charly candy params: wrote …/candy/plugin-clean/params/cue_types_gen.go     # charly resolves the module

$ go test -count=1 ./...
--- FAIL: TestCleanCategories (0.00s)
        command_test.go:108: cleanCategories: clean: the plugin schema does not compile:
        package "github.com/opencharly/spec/schema" imported but not defined in  (and 1 more errors)
```

That is this plugin's **in-process** compile of its own schema — the `cleanCategories` path, which runs
with no CUE module for `spec` in scope. Six tests fail. Making the import work would mean teaching that
path to resolve the `spec` CUE module, which is a load-path change well beyond a definition-identity fix;
the measured constraint is recorded in the schema's header instead, so the next reader inherits the fact
rather than the guess.

So: `store_budget: #CleanStoreBudget`, the same shape under a name the contract does not own. **R2 sees
two copies of a shape, and this PR does not grant itself a waiver for it:** the copy is accepted *until*
`opencharly/sdk#567` gives a plugin a module-aware compile, at which point the local def is deleted and the
field references `spec.#StoreBudget`. That issue carries the mechanism (`cuecontext.New().CompileString`
has no module context, so an `import "github.com/opencharly/spec/schema"` cannot resolve in the in-process
path), the measurement above, and two viable fixes. The VALUE is unaffected either way — 32 GiB, written
once in this file, because `spec` declares no default; the machine's ceiling comes from the user
configuration and is read through `sdk#566`.

### Also corrected, because the same edit exposed them

The field's comment and the file header had both gone stale in the `sdk#566` change and were still saying:

- the 32 GiB is *"the plugin's own declaration surface … the ONE place the ceiling is written down"* — it
  is the **fallback**; the ceiling is the machine's, in `~/.config/charly/charly.yml`;
- the schema is *"SELF-CONTAINED: … compiles STANDALONE"* as though by preference — it is self-contained
  because the in-process compile **cannot** resolve a `spec` import, which is now the reason given.

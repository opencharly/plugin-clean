# 2026.255.0920 — fix(clean): report a live-build skip explicitly, never as "0 removed"

## Summary

A live-build-guarded sweep **declines by returning an empty result**, and the CLI printed the
identical line for that and for "there was genuinely nothing to remove":

```
deep: removed 0 untagged image(s) store-wide (up to 0 B reclaimable …)
```

`candy/plugin-clean/retention.go` opened the shared dangling-image prune with
`if _, _, live := liveBuildFloor(); live > 0 { return nil, 0, nil }` — so with **any** build in
flight the verb declined, and `command.go` printed the empty result exactly as it prints an empty
store. Measured live (below, same held build-activity lock, before vs after this PR): the old
binary reported **"would remove 0 untagged image(s) store-wide (up to 0 B reclaimable)" while 82
untagged images / 18.1 GiB were sitting there removable** — and the same silent-empty pattern
covered the `--images` category's charly-labeled dangling sweep and the buildah staging sweep.
Real consequence observed: an operator saw `removed 0 untagged image(s)` while 63 large untagged
images (2-4 GB each, ~45 GB reclaimable) were present, concluded the tool was blind, and fell back
to raw `podman rmi -f` — which deletes the build-layer cache that makes the next build ~8x faster
(measured: 316/336 cache hits -> 96 s build vs 2/336 -> 1429 s).

### What changed

**1. The engine carries its decision out (no caller re-derives it).** `pruneDanglingImages`,
`pruneDanglingCharlyImages`, `pruneDeepDanglingImages` and `pruneBuildahStaging` now return a
`*retentionSkip` naming the in-flight build count, and a new `runRetentionOutcome` returns
`{Reply, DanglingSkip, StagingSkip, DeepSkip}`. `runRetention` — the `verb:retention` entry point
peer plugins call — still returns exactly the same `spec.RetentionReply`.

**2. The CLI prints the skip IN PLACE OF the removed count.** New user-visible lines, exactly:

```
dangling: SKIPPED — N build(s) in flight; images are never removed during a build (re-run when builds are idle)
staging: SKIPPED — N build(s) in flight; buildah/podman staging of an in-flight build is never swept (re-run when builds are idle)
deep: SKIPPED — N build(s) in flight; images are never removed during a build (re-run when builds are idle)
```

A skip line REPLACES its category's count line (never decorates it). Two reporting fixes ride
along: the `staging` line now prints unconditionally (it used to be omitted when empty — which hid
*both* "nothing to sweep" and "the sweep declined"), and the category printing moved into
`printRetentionResult`, whose write error is now propagated instead of dropped.

**3. The guard itself is untouched.** WHEN it fires is a deliberate safety property (an untagged
intermediate may be the parent of an in-flight build) and is unchanged; only its decision is now
observable. The candy manifest's `version:` is bumped (`2026.202.1400` -> `2026.255.0054`) per this
repo's convention for a behavior change, and the candy description documents the new lines.

## The peer leg is a NAMED batch (`retention-skip-peer-wire`), not a silent park

The PEER callers of `verb:retention` (`charly box build`'s post-build prune, `charly check run`'s
post-run prune, `charly box list tags`) receive their result as `spec.RetentionReply` — a
**CUE-generated shared type in `opencharly/spec`** whose fields are `ImageRefs / DanglingIDs /
StagingDirs / BuildDirs / CheckPaths / DeepIDs / DeepBytes / TagGroups / KeepImages /
KeepCheckRuns / Error`. It has **no field** that can carry "a guarded sweep declined", and `Error`
is wrong (it would fail a peer's prune instead of reporting a skip).

**Batch `retention-skip-peer-wire`** carries exactly that change, in one wave, in the two repos
the defect spans:

- **opencharly/spec** — add the skip signal to the shared CUE schema behind `#RetentionReply`
  (`skipped_builds: int` + `skip_reason: string`, or one `skips: [...{sweep, builds, reason}]`
  entry per guarded sweep — the shape to be decided THERE, by that repo's own rulebook) and
  regenerate `spec/cue_types_gen.go`.
- **opencharly/plugin-clean (this repo, next cutover)** — populate it from the `retentionSkip`
  signals this PR already threads out of the engine (`runRetentionOutcome`), bump the spec pin,
  and let plugin-box / plugin-check surface the same line in their own report paths.

This PR deliberately does not guess that schema: the skip signal is made observable at the surface
the operator actually reads (the plugin's own CLI, which needs no wire change), and the engine
signal it needs for the peer leg is already in place, so the batch is a small, mechanical follow-up
rather than a new investigation.

#### A separate finding, RCA'd here (not caused by this change): the second bed attempt hung

The bed was run twice against the same binary and the same tree. The **first** run
(`2026.255.0114`) completed and is the evidence above. The **second** attempt (calver
`2026.255.0122`, launched only to capture the process exit code) hung in `check-live`:

```
$ cat .check/check-commands-local/2026.255.0122/check-live.log
status: RUNNING
command: charly check live

$ ps -o pid,etime,time,pcpu,lstart -p 2161028,…   # the run's __plugin serve children
2161028  06:24:13  00:00:00  0.0  Sa Sep 12 03:22:41 2026 … __plugin serve   # x10
```

Operator-measured on the runaway tree: the parent `charly check run` process accumulated **23 s of
CPU in 6 h 22 m**, spawned `charly check live check-commands-local` children in a loop, and held
only its own per-run FLOCK on `.check/check-commands-local/.lock` (not the image store). Ten
`__plugin serve` children of that run (started 03:22:41, 0.0% CPU, 00:00:00 CPU time) were still
alive at 09:46 and were killed then.

**Root cause (RCA, evidence-backed): the VENUE binary was stale, not the change.** This is the
exact charly#588 class, already fixed upstream — **charly#591** ("bound the plugin readiness read
so a non-answering plugin can no longer hang charly forever", merged 2026-09-11T19:52Z) describes
the identical signature: *"the process parked (state S / futex_wait), its `__plugin serve` children
alive and idle at 0.0% CPU, no step output, no error, and no summary.yml for 25+ minutes"*. The
bound is the post-handshake readiness READ (`describe` → `conn.Meta.Describe(ctx, …)` issued on
`context.Background()`). The bed venue I used is a scratch charly clone at **v2026.247.1701
(2026-09-04)** — SEVEN DAYS older than #591 — and it does not contain the fix:

```
$ ls /tmp/cbx-charly/charly/plugin_connect_deadline.go
ls: cannot access '/tmp/cbx-charly/charly/plugin_connect_deadline.go': No such file or directory
$ grep -rn pluginReadyTimeout /tmp/cbx-charly/charly/            # (no output)
$ grep -rn pluginReadyTimeout <charly main>/charly/plugin_connect_deadline.go
55:  pluginReadyTimeout = 2 * time.Minute
```

So the hang is a property of the 2026-09-04 venue binary, reproducible with any plugin that
finishes the handshake and never answers — it says nothing about this PR, whose changed code is
plugin-clean's reporting, and the SAME binary completed the bed 25 minutes earlier. Two consequences
are recorded rather than dropped, and are routed to the named batch **`check-run-live-hang`**
(repo: `opencharly/charly`), which carries the residual hardening left after #591:

1. `charly check run` puts **no timeout on its `check live` subprocess** — a hang can outlive any
   budget and block the host (it did: 6 h 22 m). #591 bounds a FAILED connect's readiness read; it
   does not bound the runner's wait for its own child.
2. **`__plugin serve` children are not reaped when the runner dies unexpectedly** — #591 adds a
   teardown grace for a failed connect, but a SIGKILL'd parent left ten serve children orphaned at
   0.0% CPU for 6 h 22 m. The batch also carries the RCA of the looping `check live` re-spawn the
   operator observed.

Process discipline, applied from here on: beds are launched under `timeout` (not bare
`setsid nohup`), and the bed venue binary must be at least as new as the campaign's own fixes.


### 4. Live before/after of the SKIP itself (same held build-activity lock, same host)

The one state a unit test cannot create is a genuinely in-flight build. It was created by holding
the host-global build-activity lock charly core writes (`~/.cache/charly/locks/builds/*.lock`, an
exclusive flock held by a real build), and running both binaries under it. **BEFORE** (the same
clone, pinned `plugin-clean` v0.2026237.1417, no PR):

```
=== live build-activity lock HELD ===
$ charly clean --deep --dry-run
deep: would remove 0 untagged image(s) store-wide (up to 0 B reclaimable — shared layers may reduce actual reclaim; pair with --invalidate for the fullest reclaim)
$ charly clean --dry-run
images: would remove 41 tag(s) (keep_images=3)
dangling: would remove 0 untagged charly image(s)
build: would remove 0 staging dir(s) under .build/_candy (keep_images=3)
```

**AFTER** (the PR tree):

```
=== binary: 2026.247.1702 (built with this PR) — same lock HELD ===
$ charly clean --deep --dry-run
deep: SKIPPED — 1 build(s) in flight; images are never removed during a build (re-run when builds are idle)
exit=0
$ charly clean --dry-run
images: would remove 41 tag(s) (keep_images=3)
dangling: SKIPPED — 1 build(s) in flight; images are never removed during a build (re-run when builds are idle)
staging: SKIPPED — 1 build(s) in flight; buildah/podman staging of an in-flight build is never swept (re-run when builds are idle)
build: would remove 0 staging dir(s) under .build/_candy (keep_images=3)
exit=0
=== lock RELEASED ===
$ charly clean --deep --dry-run
deep: would remove 82 untagged image(s) store-wide (up to 18.1 GiB reclaimable — shared layers may reduce actual reclaim; pair with --invalidate for the fullest reclaim)
exit=0
```

That is the defect and the fix in one frame: the declined sweep that used to print "0 untagged
image(s), 0 B" while 82 such images (18.1 GiB) sat in the store now says `SKIPPED — 1 build(s) in
flight`, and the moment the build is idle the same binary reports the real work (`would remove 82`).
Nothing was removed in any of these runs (all `--dry-run`), and the temporary lock file was removed
afterwards.

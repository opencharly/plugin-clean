# 2026.287.2341 — fix(clean)!: the image-tag inventory resolves the RUN engine, not the retired builder field (opencharly/opencharly#481 leg 7)

## Summary

**Leg 7 of `opencharly/opencharly#481` (`plugin-clean`), and it is a REPOINT rather than a retirement.** `resolveEngineBinary` read `rt.BuildEngine` — the IMAGE BUILDER — to name the **container engine** binary the image-tag inventory shells. Once the builder became BuildKit (operator scope: the image BUILDER only) that field was wrong twice over: it is gone from the contract (spec leg 1), and BuildKit is not a container engine at all, so it could never name a binary that runs containers.

What this consumer needs is an engine that **runs** containers, and `engine.run` is where charly names one — the same resolution the SDK's own siblings make (`sdk/deploykit/box_ref.go:206`, `container_resolve.go:37`: `kit.EngineBinary(rt.RunEngine)`). `engine.build` has no successor; **this consumer's need does**, and it was always the run engine's job.

- The decision is **split from the binary mapping** — `resolveEngineName` + `resolveEngineBinary` — so it is testable in its own right. The reason is a fallback that makes a control blind: **`kit.EngineBinary` falls back to the default engine when the engine op fails**, so a test comparing only binaries could not tell a wrong engine name from an unresolvable host.
- Pins adopted producer-first: `spec v0.2026287.1848` + `sdk v0.2026287.2213`. `go build ./...` named **exactly one** site — the compiler did the migration's bookkeeping.
- The bed gained `cc-images-engine-resolves`, which drives the changed path on the real binary and asserts **the command's own exit status** from a retained log, never a pipeline's.

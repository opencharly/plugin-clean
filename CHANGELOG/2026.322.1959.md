# 2026.322.1959 — feat(clean): the store ceiling is the machine's, authored in the user configuration (#28)

## Summary

**Successor to opencharly/plugin-clean#33**, which the validator auto-closed at its 5-verdict threshold
after each of its findings had been fixed and re-run. Same branch, same head; this body names its
predecessor (Part II #7's carry-forward).

`charly clean --store` measures the image store against the **machine's** ceiling, not a plugin-wide
constant and not a project setting: the machine authors `clean: {store_budget: {bytes: …}}` in its user
configuration, this PR reads it through the section reader `sdk#566` added, and the report names the
provenance. The executed arm below shows the value arriving, the fallback when nothing is authored, and
the refusal when what is authored is not a positive ceiling. The machine authors it in its user configuration —
`~/.config/charly/charly.yml`, the per-host file `D-STORE-2` (`DESIGN.md:2483`) makes the home for what
the user sets — as a declared section beside `cache:`/`ledger:`/`deploy:`/`system:`:

```yaml
clean:
  store_budget:
    bytes: 274877906944      # 256 GiB
```

The section and its `#StoreBudget` are declared in `opencharly/spec#384`; the value reaches this plugin as
`*spec.CleanSection`, read over the reverse channel by **`loaderkit.LoadHostCleanSectionViaExecutor`** — the
section-scoped reader `opencharly/sdk#566` added, because the `deploykit.DeployConfig` route runs the
section through `ProjectDeployConfig` and drops it. **No wire field, no resolver of this plugin's own, no
new seam** — and therefore no sdk API change here; this PR consumes two pins (`spec v0.2026322.1814`, `sdk v0.2026322.1913`), the second
because `sdk#566` is what delivered the section reader this depends on.

### Three states, and never a sentinel

| State | Effective ceiling | Source in the report |
|---|---|---|
| absent — nil at **every** level (no file, no `clean:`, no `store_budget:`) | 32 GiB, the plugin's `#CleanPlugin.store_budget` | `ceiling: plugin default` |
| authored and positive | the authored number | `ceiling: user config` |
| **unreadable**, or authored **non-positive** | **REFUSED**, naming the file | — |

The third row is the point. Falling back to 32 GiB because the configuration could not be *parsed*
would evict a machine's builds under a ceiling it never wrote — the same "an unreadable surface is not
an empty one" rule this category already applies to the state inventory, applied to configuration. And
`0` is never read as "absent": `int64`'s zero cannot distinguish them, so presence is the field's
nil-ness, never a number.

`bytes` is `int & >0`, projected as **`int64`** (`@go(Bytes, type=int64)`): 256 GiB is
`274877906944`, which overflows a 32-bit `int`, and on `386`/`arm` that overflow is a silent wrap, not
a compile error — the precedent is `disk_size_bytes`. The package carries `int64` from the decode to
`kit.HumanBytes`, never a float.

### One consequence, stated rather than discovered

Because the configuration is read over the reverse channel, **`--store` now requires compiled-in
placement**, joining `--images`/`--check`/`--deep`. `--cache`, `--scopes`, `--build-cache`, `list` and
`--invalidate` still run out-of-process. The docs (README, the authored `clean` skill, the candy
description) say so, and the out-of-process refusal is the first live arm below.

### What this is not

It is not project tunability, and it does not add a `defaults:` field: a store's ceiling belongs to the
machine. It also does not close `opencharly/spec#383` — §4.6's `get config` op ("the caller's own
user-configuration section") is still unimplemented, and the knob reads through the whole-file loader
the tree provides. That is honest for the value (the field is the machine's, and the plugin reads only
that field) but broader than the contract intends; the narrowing stays tracked there.

## Change classification

**Breaking change + rollback:** one consumer-visible narrowing and no breakage. `--store` now requires
compiled-in placement (it reads the machine's configuration over the reverse channel), which is a
placement requirement the other three resolved-default categories already carry and which the docs
state; every other CLI category is unchanged. The CUE schema in this repo is untouched (the fallback is
the same `#CleanPlugin.store_budget`). The pins move to `spec v0.2026322.1814` and
`sdk v0.2026322.1913` (the reader is `sdk#566`'s). Rollback is `git revert` of these commits: the
resolution reverts to the 32 GiB fallback, and no state is written by any of it.

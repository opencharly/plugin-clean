# 2026.261.0029 — fix(deps): adopt the shared sdk/spec pins so the plugin builds for 32-bit ARM

## Summary of changes

Adopts the fixed shared `sdk`/`spec` pins so this plugin builds for **32-bit ARM (armv7)**, and exercises the re-pinned plugin live.

- `README.md`: a Platforms section documenting that the module builds for `linux/amd64`, `linux/arm64`, `linux/arm/v7` and `linux/386` — the two 32-bit targets being what this change enables.
- `candy/plugin-clean/go.mod` + `go.sum`: `sdk` v0.2026234.347 → `v0.2026260.1434`, `spec` v0.2026232.520 → `v0.2026259.2033`. No source change. The branch carries four commits — the pin adoption and three README revisions (the platform note, its R4a scoping fix, and the added 386 target) — which the org's squash-merge collapses into one.

- `go.mod` — the two contract pins (`sdk`, `spec`; `spec` is a DIRECT require in this module), plus the `golang.org/x/*` bumps whose width the sdk pin carries:
  - `// indirect` requires: `net`, `sys`, `term`, `text`.
- `go.sum` — the same two contract pins, plus the full transitive `x/*` refresh: `crypto` v0.52.0→v0.54.0, `mod` v0.35.0→v0.37.0, `net`, `sync` v0.20.0→v0.22.0, `sys`, `term`, `text`, `tools` v0.44.0→v0.47.0.
- **the two module-identity rehomes** in `go.sum` (the candy de-submodule cutover showing up in this module's graph): `github.com/opencharly/charly/candy/plugin-egress` → `github.com/opencharly/plugin-egress/candy/plugin-egress v0.2026237.1419`, and `github.com/opencharly/charly/candy/plugin-init` → `github.com/opencharly/plugin-init/candy/plugin-init v0.2026237.1424` — both `// indirect`, no `replace`.

**Root cause:** `sdk/buildkit` did not compile for 32-bit targets — `syscall.Statfs_t.Bsize` is `int32` on `arm`/`386` but `int64` on `amd64`/`arm64`, so `buildkit/privileged_runner.go`'s `int64(st.Bavail) * st.Bsize` was a type mismatch off the 64-bit targets (opencharly/sdk#262, fixed in opencharly/sdk#263, merged tag `v0.2026260.1434`). Every module importing `sdk/buildkit` — this plugin included — therefore failed to build for armv7 until its own sdk pin moved.

**Closes / relates to:** depends on `opencharly/sdk#263` (merged), closes the armv7 gap tracked as `opencharly/sdk#262`. Part of the armv7 delivery for `opencharly/plugin-jetkvm`.

**Breaking change + rollback:** `none` — a dependency pin with no API or CLI change. Revert the merge to roll back.

## Change class

`charly-or-sdk Go` — a dependency-pin adoption in a plugin module; no source change.

**The armv7 binary executes on real 32-bit ARM.** The same plugin built for armv7 is copied to a Rockchip RV1106 `armv7l` device (over ssh) and executes there — it loads and runs its own code path to its natural conclusion:

```console

```

The one line is the command's own out-of-process guard. The same binary on the amd64 host produced the analogous result through `charly` (the exit-0 dispatch above).

**RCA on the exit code.** The device has no `charly` host to dispatch to, so the plugin takes its own no-host path and exits 1 with the line pasted above — its own guard or argument handling, running. That is not a crash, a signal, or an `exec` failure: the armv7 ELF loads and executes, which is this PR's claim. On the amd64 host, dispatched through `charly`, the same plugin reaches exit 0 (the live-dispatch block above).

This host has no armv7 binfmt (`podman run --platform linux/arm/v7 alpine uname -m` → `exec format error`), so the device is the available armv7 execution target; it is a physical appliance, NOT a `disposable: true` charly target, so the binary is only copied and executed — no charly deploy is applied and nothing is mutated on it.
